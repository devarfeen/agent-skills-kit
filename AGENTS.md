# Agent Instructions — agent-skills-kit

Hand-authored conventions for working in this repo (not generated by the
`agents-md` skill — that skill targets `.code-workspace` roots; this is a single
repo). Sibling `CLAUDE.md` and `GEMINI.md` are redirect shims; this file is the
source of truth.

This repo is a library of agent skills: markdown instruction bundles under
`skills/`, installed standalone into AI coding CLIs. There is no application
code. Editing here means editing instructions that other agents will execute,
so precision beats volume.

## Rules

1. **Run `bash tools/validate.sh` before every commit.** It enforces frontmatter,
   manifest coverage, ship-policy parity, link integrity, and zero-attribution.
   CI runs it on every PR. `tools/hooks/pre-commit` runs it automatically once
   `git config core.hooksPath tools/hooks` is set.
2. **Respect the sync map** in [CONTRIBUTING.md](CONTRIBUTING.md): a new/renamed
   skill needs a `skills-manifest.md` row, a README table row, and its path in
   one `.claude-plugin/marketplace.json` plugin group; the two
   `ship-policy.md` copies stay byte-identical; template changes in `agents-md`
   bump its version marker; a new or moved skill updates the `ask-kit` map; a
   behavior change gets a dated `CHANGELOG.md` entry. Check `.out-of-scope/`
   before proposing a change that may already be declined.
3. **Know the audience before editing a file.** `skills/*/SKILL.md` and
   `references/` are model-facing (loaded into agent context; every sentence
   costs tokens). `README.md`, `GUIDE.md`, `BEST-PRACTICES.md`, `CONTRIBUTING.md`
   are human-facing and must never be loaded into a generated `AGENTS.md` or shim.
4. **Zero attribution.** Never add or leave co-author, AI, or tool attribution
   in commits, PR titles/bodies, issue comments, release notes, generated docs,
   or code comments — no `Co-authored-by:`, `Generated by`, `Made with`,
   `AI-assisted`, or agent signature footers. Strip tool-injected attribution
   before committing or publishing.
5. **Small, focused commits.** One concern per commit, imperative-leaning
   subject. Skill content changes and doc-index changes may share a commit only
   when the sync map requires them to move together.
6. **Don't vendor companions.** Matt Pocock's skills, MCPs, and other companions
   are separate installs referenced by name only.
7. **Preserve refusal boundaries.** When editing a skill, keep its "stops and
   refuses" lines (never auto-chain, scope gates, cosmetic-only, etc.) — they
   are the safety property, not filler.
8. **Write human-facing docs in plain English.** `README.md`, `GUIDE.md`,
   `BEST-PRACTICES.md`, `CONTRIBUTING.md` and `CHANGELOG.md` are read by
   people, not models. Lead with what the reader should do and a real command
   (`/factory 87`), use short sentences and "you", and explain any term a
   newcomer would not know (head, marker, unit, gate) or drop it. When there is
   a choice, add a small "which one to use" table. Keep every fact, command and
   refusal boundary; plain does not mean vaguer. Model-facing files keep their
   terse style.
9. **Apply Cursor unslop automatically.** Before sending agent-written prose or
   finalizing written content, read and apply the installed Cursor `unslop`
   rules. Prefer project-local over user-level runtime skill paths; reuse the
   file while unchanged and reload after context loss or changed resolution.
   This authorizes reading the explicit-only helper, not Skill-tool invocation
   when disabled, upstream metadata edits, or additional workflow actions.
   Preserve meaning, evidence, qualifications, technical literals, quotations,
   required templates, markers, headings, field labels, and canonical text.
   Leave unrelated prose alone. If unavailable, report once and continue under
   existing writing rules.
